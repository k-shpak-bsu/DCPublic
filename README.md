# Параллельные вычисления. Proof-of-Work

## Что здесь происходит

В этом репозитории — приложение для исследования параллельных вычислений на CPU. Программа решает 100 независимых задач Proof-of-Work: для каждой задачи нужно подобрать число, при котором SHA-256 начинается с заданного количества нулевых бит. Это реальные вычисления SHA-256, без искусственных задержек и заранее подготовленных ответов.

Ваша задача — реализовать алгоритм, который распределяет вычисления между воркерами и находит все 100 решений. Затем сравните время работы с одним воркером и с несколькими. Поэкспериментируйте и подумайте, почему увеличение числа воркеров не всегда даёт пропорциональное ускорение.


### Структура солюшена

Солюшен состоит из двух проектов:

`DC.Compute` — здесь находятся вычислительные алгоритмы. Основные изменения вы делаете в этом проекте. Интерфейс `IPowSolver` задаёт способ запуска решения, а в `PowModels.cs` описаны результаты и сообщения о прогрессе. `PowSolver.cs` — базовая реализация не очень эффективная, в чем вы можете убедиться, попробовав распараллелить с числом воркеров равным максимальному количеству доступных вам логических процессоров. Вы должны попытаться сделать более эффективное решение. `PowTelemetry.cs` собирает необязательные измерения для графиков.

`DC.App` — WPF-приложение для запуска вычислений. Здесь находятся ввод параметров, графики, вывод результатов и независимый валидатор. Для подключения нового решения нужно добавить его в список `_implementations` в начале `MainWindow.xaml.cs`. Сам валидатор менять не нужно.


### Работа с UI

Seed — строка ровно из шести цифр от 0 до 9. Например, `000123` — корректное значение, начальные нули сохраняются. Одинаковые seed и сложность задают одинаковый набор задач для разных реализаций.

Сложность задаётся числом от 1 до 24, по умолчанию — **20 бит**. Для быстрой проверки правильности можно вручную поставить меньше бит. Число задач всегда равно 100. Число воркеров можно выбрать от 1 до 100; по умолчанию используется число доступных логических процессоров, но не больше 100.

`Cancel` отменяет текущий поиск. Уже полученные результаты остаются доступными для просмотра и проверки. Если решений не хватает, валидатор сообщит об этом. При закрытии окна приложение отменяет вычисления и ожидает завершения воркеров.

### Как устроена задача

Для каждого `taskId` от 0 до 99 нужно найти `nonce`, для которого выполняется условие:

```text
SHA256(UTF8("BSU-POW-1|{seed}|{taskId}|{nonce}"))
```

В начале полученного хеша должно быть не меньше `difficultyBits` нулевых битов. Биты проверяются от старших к младшим. Например, сложность 12 означает, что первые три шестнадцатеричные цифры хеша должны быть нулевыми.

`nonce` — беззнаковое 64-битное целое число, в C# это `ulong`. Подходит **любой** nonce, который удовлетворяет условию. 

Формат строки нужно соблюдать точно: префикс `BSU-POW-1`, разделители `|`, UTF-8 без BOM. `taskId` и `nonce` записываются десятичными цифрами без начальных нулей и разделителей разрядов, независимо от региональных настроек. Начальные нули в seed, наоборот, являются частью строки и сохраняются.

Результат должен содержать ровно 100 пар `TaskId` и `Nonce`. Каждый номер задачи от 0 до 99 должен встретиться один раз. Порядок записей значения не имеет.

### Реализация своего решения

Добавьте в `DC.Compute` класс, который реализует `IPowSolver`. У интерфейса один метод:

```csharp
Task<PowResult> SolveAsync(
    string seed,
    int difficultyBits,
    int workerCount,
    IProgress<PowProgress>? progress,
    CancellationToken cancellationToken,
    PowTelemetry? telemetry = null);
```

Метод получает параметры запуска и возвращает решения вместе со статистикой. В `PowResult` входят найденные nonce, прошедшее время, число завершённых задач, запрошенное число воркеров и количество вычисленных хешей.

Вычисления должны идти в фоновых потоках и действительно выполняться параллельно, когда это позволяет оборудование. Просто добавить `async` к методу недостаточно. Код библиотеки не должен обращаться к WPF-контролам.

Через `progress` можно сообщать о ходе работы. В `PowProgress` значение `Solution == null` означает начало обработки задачи, а заполненное `Solution` — получение ответа. `CancellationToken` нужен для отмены: проверяйте его в процессе поиска и завершайте работу всех созданных воркеров перед возвратом из метода.

Последний параметр, `telemetry`, нужен для подробных графиков. Если он передан, вызовите `Start` перед вычислениями. `BeginWork` отмечает назначение воркеру задачи и возвращает номер его полосы на графике, `AddAttempts` добавляет выполненные попытки, `EndWork` завершает интервал назначения, а `Solved` отмечает найденное решение. После завершения всех воркеров вызовите `Finish`, в том числе при отмене или ошибке. Эти вызовы показаны в существующих реализациях. Счётчики обновляйте порциями, а не после каждого хеша: иначе сами измерения будут заметно мешать вычислениям.

Реализация может игнорировать `telemetry`, но тогда подробные графики не получат данных. 


### Проверка результатов

В `DC.App/MainWindow.xaml.cs` находится метод `ValidateButton_Click`, выделенный комментариями `INSTRUCTOR VALIDATOR - DO NOT MODIFY`. Вся проверка реализована непосредственно в этом обработчике. НЕ изменяите эту часть кода. Я проверю. В целом вам незачем изменять WPF проект.

Валидатор берёт seed и сложность, которые приложение сохранило перед запуском. Он проверяет число записей, наличие всех номеров от 0 до 99, отсутствие дубликатов и допустимость nonce. Затем самостоятельно восстанавливает строки, вызывает `SHA256.HashData` и проверяет нулевые биты. Для полного корректно оформленного набора при каждом нажатии заново вычисляются 100 хешей. Функции проверки и готовые хеши из решателя не используются.

`PowSolution.Nonce` имеет тип `ulong`, поэтому отрицательное, дробное или слишком большое значение через эту модель передать нельзя. Пропуски, дубликаты, недопустимые номера задач и nonce, которые не подходят по сложности, валидатор отмечает отдельно. Ничего автоматически не исправляется и не досчитывается.

Надпись о завершении вычислений ещё не означает, что ответы правильные. Результат нужно проверить кнопкой `Validate All Results`. Для просмотра всех nonce раскройте `Individual nonces`. Кнопка `Copy Results as JSON` копирует исходные параметры запуска и ответы в буфер обмена.

### Метрики и графики

На вкладке `Live execution` показаны число решённых задач и производительность в хешах в секунду. После запуска с одним воркером появляется измеренная опорная кривая для такого же seed, сложности, реализации и режима измерений.

Здесь же есть график назначенной работы и потребления CPU, а также тепловая карта воркеров. **Тёмная полоса означает, что воркеру назначен поиск, а не что он непрерывно выполняется на процессоре.** В этот интервал входит ожидание CPU. 

Кривая CPU использует учёт процессорного времени текущего процесса. Например, 6 CPU-секунд за одну секунду реального времени соответствуют в среднем шести занятым логическим процессорам. Сюда входит работа интерфейса и среды .NET. Это отдельная метрика; ни она, ни занятость воркеров не равны эффективности распараллеливания.

На вкладке `Puzzle durations` показаны длительность каждой задачи и гистограмма. Можно переключиться между временем и количеством попыток. Время считается от первого назначения до сообщения о решении; для cooperative сюда входят паузы между пакетами. Оранжевые столбцы — ещё не завершённые задачи, их окончательное время пока неизвестно. Гистограмма включает только решённые задачи, поэтому во время работы в ней сначала преобладают быстрые задачи.


На вкладке `Speedup & limits` показаны измеренное ускорение по времени и рост производительности в хешах в секунду. Пунктирная линия `p×` — ориентир идеального ускорения.

Графики обновляются примерно четыре раза в секунду. Флажок `Collect live measurements` включает подробные измерения. Они тоже расходуют процессорное время, поэтому для более чистого сравнения времени их можно отключить перед запуском. Запуски с включёнными и выключенными измерениями сравниваются раздельно.

### Как сравнивать результаты

Сначала выполните запуск с одним воркером, затем с 2, 4, 6, 8, 12 или другим подходящим количеством. Сохраняйте seed, сложность, реализацию и режим измерений. Для сравнения двух реализаций меняйте только выбранный алгоритм.

Ускорение и эффективность считаются так:

```text
Ускорение(p)     = Время(1) / Время(p)
Эффективность(p) = Ускорение(p) / p
```

Для эффективности в процентах умножьте результат на 100. Идеальная эффективность — 100%, идеальное ускорение — `p`.
